## 7. 如何对应端到端、采信长度和profiling

| 端到端客户端实际统计 | Baseline | Top-K |
|---|---|---|
| 首token后实际输出token总数 | 392832.000000 | 392832.000000 |

| 实际每chunk输出token | 4.008244 | 4.545562 |
| 加权平均chunk间隔 ms | 103.462620 | 107.622218 |

两组输出长度一致，TPOT × 客户端实际平均chunk长度 = 客户端加权平均chunk间隔：

```text
Baseline: 25.812453 × 4.008244 = 103.462620 ms
Top-K:    23.676329 × 4.545562 = 107.622218 ms
```

因此TPOT更低不要求每轮更短：本轮每次返回的token更多，即使端到端加权返回间隔增加4.02%，按token分摊仍更快。服务端平均采信长度4.0183/4.5575与客户端实际chunk长度略有差别，首token及长度上限截断等记账口径不同。384条混合prefill/不同上下文的平均返回间隔也不能强行等于32请求稳态profiling周期97.39/96.60ms。

Profiling收益闭合：

```text
融合MoE: 24.6751 - 20.5430 = 4.1321 ms
图内新增裁剪:                 0.9681 ms
Target其余kernel净增加:       0.1395 ms
再计图内等待/拷贝/间隙变化，Target实际省 2.9222 ms
图外增加: 45.3474 - 43.2165 = 2.1309 ms
整轮净省: 2.9222 - 2.1309 = 0.7912 ms
0.7912 / 97.3909 = 0.81% 周期缩短
```

## 8. 编译与结论边界

本轮384条运行前后_prune_routes缓存138→138，新增/变化0个。结合此前独立冷缓存不同N复用一个内核的实卡回归，支持按行数重复编译的问题已修复。这里只检查裁剪内核，不代表其他代码完全没有编译或所有长尾都已消失。

可以报告：实际预算减少、融合MoE更快、target图更短；图外增长抵消约72.9%的图内节省。此次端到端结果更快，但接受情况、物理卡放置和外部上下文都有变化，未做重复独占同卡实验，不能将+7.80%视为已隔离的算法收益。不能从融合总时间直接拆出通信/GMM各自收益。
